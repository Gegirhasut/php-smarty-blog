# План работы

Исходный пошаговый план, по которому шла разработка. Каждый этап - отдельные коммиты, после этапа - ревью и только потом push.

## Стек и решения
- Блог «Агентура» - об ИИ. Название, описание и адрес сайта - в `Config`, шаблоны и SEO берут их оттуда.
- Локально: PHP 8.5-fpm, nginx и MySQL 8.4 в Docker Compose, отдельными контейнерами. Из Composer в рантайме только `smarty/smarty` ^5.
- Front controller `public/index.php` + свой маленький роутер с ЧПУ: `/`, `/category/{slug}?sort=date|views&page=N`, `/post/{slug}`,
  а также `/sitemap.xml`, `/feed.xml`, `/llms.txt` и `/robots.txt`.
- PDO и только prepared statements; Smarty экранирует вывод по умолчанию; сортировка - по белому списку.
- Серверный рендеринг, страницы работают без JS.
- SCSS собирает dart-sass из стадии `sass` в Dockerfile (бинарник без Node.js): в разработке - сервис `sass` в compose
  с `--watch`. Собранный CSS в git не попадает.

## Архитектура
Тонкие контроллеры, весь SQL в репозиториях, Smarty только выводит. Зависимости передаются через конструктор
и собираются в одном месте, без DI-контейнера. Без статического и глобального состояния, каждый класс отвечает за одно
и тестируется. Простота важнее «энтерпрайзности». Соединение с БД открывается лениво при первом обращении:
404 и 405 обходятся без него, а в тестах фабрика соединения подменяется.

## База данных
- `categories` (id, name, slug, description)
- `posts` (id, title, slug, image, description, content, views, published_at); `published_at` хранится в UTC.
  Обложка (`image`) необязательна: в ТЗ поле есть, но обязательным не названо.
- `category_post` (category_id, post_id, position, published_at, views) - связь многие-ко-многим, FK с каскадным удалением.
  `position` - порядок категорий статьи из её файла сидера, первая по порядку - основная: она в хлебных крошках, первой среди меток
  и выбирает заглушку для статьи без обложки. `published_at` и `views` - копии полей статьи для индексов ленты категории.
- slug - латиница в нижнем регистре, цифры и дефисы: колонка в ascii, другие строки сидер не пускает, а репозитории не ищут.
- Схема - `database/schema.sql`, применяется целиком из `bin/seed.php`; изменения - через `--fresh`, данные учебные, миграций нет.
  Индексы: UNIQUE slug, `posts(published_at)` под свежие статьи блога, узкий `posts(id, published_at, slug)` под sitemap,
  `category_post(category_id, published_at, post_id)` и `(category_id, views, post_id)` под ленты категорий, главную и похожие,
  UNIQUE `category_post(post_id, position)` под категории статьи по порядку.
- Репозитории возвращают сущности (`Category`, `PostCard`, `Post`), строки результата читаются через `Row` с проверкой типов.
- Текст статьи хранится простыми блоками: абзацы, подзаголовки `## ` и пункты списка `- `; выводится с экранированием,
  без сырого HTML.
- Главная: одним запросом через `JOIN LATERAL (... LIMIT 3)` на категорию, не больше 3 на категорию; пустые категории не попадают.
- Порядок категорий в меню и на главной - по id, то есть как в `categories.php`: порядок задаёт редакция, отдельная колонка не нужна.
  Категории без статей не показываются нигде, кроме собственной страницы.
- Категория: `COUNT` + `LIMIT/OFFSET` (9 статей, сетка 3×3), сортировка по просмотрам или дате, плюс id для стабильного порядка;
  `ORDER BY` выбирается через `match` по enum `Sort`, а не подставляется из запроса. id страницы берутся из индекса связки
  по категории и дате (просмотрам), строки статей - только для них, поэтому скорость не зависит от доли категории в блоге.
  Глубокий `OFFSET` проходит пропущенные записи этого индекса: десятки миллисекунд на 36 000 статей; дальше - keyset-пагинация.
- Статья: просмотр - один `UPDATE` статьи и её связей (`views = views + 1` в самой базе), только на GET; похожие - по числу общих категорий среди 50 последних статей каждой категории статьи, затем новее, без самой статьи, 3 штуки.
- Сидер `php bin/seed.php [--fresh]`: категории и статьи с 1-3 категориями, датами и просмотрами из PHP-файлов
  в `database/seeds/`, вставка одной транзакцией. Обложка задана в файле статьи (`'image' => '<категория>-N.webp'` из `images/`),
  соседние в ленте по дате статьи одной категории получают разные; используемые обложки копируются в `public/uploads`.

## SEO и скорость
- Семантическая разметка, один `h1`, хлебные крошки, `lang="ru"`.
- Свои title, description, canonical, Open Graph и Twitter Card на каждой странице; JSON-LD (`WebSite`, `BreadcrumbList`, `CollectionPage`, `BlogPosting`).
- Сортировка не плодит дубли. `?sort=date` и `?page=1` - 301 на адрес без них: это та же страница, а редирект склеивает адреса
  надёжнее, чем подсказка canonical. Мусорные `sort`/`page` и страница после последней - 404: подставить первую страницу значило бы
  отдавать дубль с кодом 200.
- canonical категории - без значений по умолчанию, со страницей больше первой. Список по просмотрам - `noindex, follow`, а не canonical
  на список по дате: на одной и той же странице у них разные статьи, и такой canonical поисковик счёл бы ошибкой.
- Индекс `/sitemap.xml`: главная и категории в одном файле, статьи - в файлах по 1000 (диапазоны id), у адресов `lastmod`;
  `/robots.txt` со ссылкой на индекс. RSS 2.0 `/feed.xml` и `/llms.txt` (формат llmstxt.org,
  по 20 свежих статей на категорию и ссылка на sitemap: размер не зависит от числа статей) - тоже из базы.
  Адреса собирает один класс `Urls`.
- Картинка для соцсетей у страниц без обложки - `/og.jpg` (1200×630) из `Config`.
- Картинки с размерами, `loading="lazy"`, первая на экране - `fetchpriority="high"`.
- Один минифицированный CSS с версией в адресе (модификатор Smarty `asset` дописывает `?v=` со временем изменения файла),
  gzip, кэш на год для `/assets/` и 30 дней для обложек и иконок в nginx, OPcache в проде. Цель - Lighthouse 95+.
- Доступность: контраст AA, `alt`, видимый фокус, `aria-current`, ссылка «Перейти к содержимому», `prefers-reduced-motion`.

## Вёрстка
- Макеты - `docs/design/` (главная, категория, статья, логотип). Статья на макете - узкая колонка по центру;
  по решению владельца она шире: две колонки, текст и сайдбар от одного левого края. Поиска и ссылок подвала
  («О блоге», «Контакты», соцсети) с макетов нет намеренно: таких страниц в ТЗ нет, в подвале только RSS.
- Широкий контейнер до 1440px, mobile-first, брейкпоинты 640, 1024 и 1280px. SCSS в `assets/scss`: `abstracts` (брейкпоинты
  и миксины), `base` (шрифт, CSS-переменные темы, сброс, база), `layout` (контейнер, шапка, подвал), `components` - BEM-блоки,
  `pages` - стили отдельных страниц. Без CSS-фреймворков; состояние (текущая категория, сортировка, страница) стилизуется
  по `aria-current`, а не отдельным классом.
- Шрифт Manrope (SIL OFL) свой, не с Google Fonts: вариативный woff2, только кириллица и латиница - два файла на все
  начертания, ~40 КБ, `font-display: swap` и preload. Системный шрифт был бы легче, но на Windows и macOS выглядит
  по-разному и далёк от макетов.
- Иконки - inline SVG из Lucide (лицензия ISC) в `partials/icon.tpl`; иконка категории выбирается по slug
  в `partials/category-icon.tpl`: это оформление, а не данные, поэтому в шаблоне, а не в базе.
- Меню на телефоне открывается без JS: флажок перед списком и `:checked` в CSS, работает с клавиатуры.
- На телефоне три статьи секции главной - ряд с прокруткой вбок, а не столбик: страница короче в два раза, статьи все на месте.
- Коралловый `#ff6b4a` - только акценты; у кнопки с белым текстом он темнее (`#cf4428`), иначе контраст ниже AA.
- Статья без обложки: в карточке - заглушка её основной категории того же размера (`partials/placeholder.tpl`,
  у категории без своей заглушки - общая), на странице статьи блока обложки нет, в соцсетях и JSON-LD - картинка сайта.
  В демо-данных такая статья одна: одна заглушка на странице выглядит намеренно, несколько рядом - как поломка.
- Логотип, иконки для телефона (web manifest, 192 и 512, apple-touch-icon), картинка баннера, OG-картинка и заглушки
  обложек заказаны у ChatGPT, в вёрстке только подключены.

## Тесты и качество
- PHPUnit и PHPStan - только dev-зависимости (инструменты, не фреймворк приложения).
- Unit: роутер, запрос, пагинация, SEO-мета, экранирование, разбор `sort`/`page`.
- Интеграционные на настоящем MySQL (база `blog_test`, в CI - сервис mysql:8.4): выборка главной, сортировка и пагинация, похожие статьи, просмотры.
- Функциональные: коды ответов, мета-теги, sitemap, robots, RSS, llms.txt.
- GitHub Actions гоняет анализ и все тесты на каждый push.

## Этапы
1. **Каркас** (готово) - Composer, Docker, точка входа, роутер, layout на Smarty.
2. **Инструменты** (готово) - PHPUnit, PHPStan, CI, тесты на каркас; документация процесса.
3. **База и сидинг** (готово) - схема, подключение, сидер, интеграционные тесты.
4. **Страницы** (готово) - главная, категория (сортировка и пагинация), статья (просмотры и похожие), sitemap и robots,
   RSS и llms.txt; разметка под макеты без стилей.
5. **Вёрстка** (готово) - SCSS по новым макетам, сборка CSS с версией в адресе, адаптив под мобильные. Макеты, логотип,
   иконки для установки на телефон (web manifest, 192 и 512, apple-touch-icon) и OG-картинку по умолчанию заказываем
   у ChatGPT, в вёрстке только подключаем.
6. **README и документация** (готово) - короткий README со скриншотами (десктоп и мобильный), документация по архитектуре,
   БД и использованию ИИ.
7. **Финальное ревью** - свежий ревьюер, проверка в браузере на десктопе и мобильном, сверка с ТЗ по пунктам.

## Порядок каждого этапа
Разработка с локальными коммитами и тестами → независимое ревью (ревьюер видит только код и ТЗ) → исправления →
повторное ревью, пока замечаний нет → моя проверка → push.
