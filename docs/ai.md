# Как использовался ИИ

ИИ использовался много: код писали агенты по моему плану и требованиям, ревью делал отдельный агент, графику рисовал
ChatGPT. Стек, архитектура, требования и приёмка каждого этапа - мои.

## Инструменты

- **Claude Code** - разработка и ревью. Каждый этап плана выполнял агент-разработчик. После этапа - отдельный
  независимый агент-ревьюер: он видит только код и ТЗ, а не переписку и рассуждения разработчика. Дальше круги
  «ревью → правки → повторное ревью», пока замечаний не останется.
- **ChatGPT** - графика: макеты страниц (`docs/design`), логотип, иконки сайта, картинка для соцсетей, баннер главной,
  обложки статей и заглушки категорий. Задача была - простой аккуратный дизайн без вау-эффекта; в вёрстке картинки
  только подключены.
- Тексты демо-статей сгенерированы с помощью ИИ.

## Процесс

1. Сначала пошаговый план - [plan.md](plan.md): стек, архитектура, схема базы, SEO, вёрстка, этапы.
   Правила для агентов (код, тесты, порядок работы) - в `CLAUDE.md`.
2. Работа строго по этапам: каркас → инструменты → база и сидинг → страницы → вёрстка → документация и демо →
   финальное ревью. Коммиты небольшие и по ходу работы, история git повторяет ход разработки.
3. После этапа - ревью и исправления, затем моя проверка и только потом push. Перед push все тесты и PHPStan зелёные.

## Что находило ревью

- **500 на кириллическом адресе.** Колонка slug в `ascii_bin`, и MySQL отказывался сравнивать её со строкой с кириллицей:
  `/post/статья` отвечал 500 вместо 404. Теперь формат slug проверяется до запроса, а сидер такие slug не пускает.
- **Терялась основная категория статьи.** Категории статьи читались в порядке меню, и в хлебные крошки попадала
  не та, что указана первой в файле статьи. Появилась колонка `position`; позже ревью уточнило, что основной считается
  категория с наименьшей позицией, а не только с нулевой.
- **Горизонтальная прокрутка главной на узких телефонах** - страница была шире экрана, исправлено в вёрстке.
- **Лишние слои и переусложнение каркаса** - убраны. Ревью следило и за направлением зависимостей: сущности собирают
  репозитории, предметная область о базе не знает, у сидера нет цикла зависимостей с репозиториями.
- **Дубли страниц.** `?sort=date` и `?page=1` отдавали ту же страницу с кодом 200 - теперь 301 на адрес без них,
  мусорные параметры - 404. В llms.txt статья из нескольких категорий повторялась - теперь она один раз, в основной.
- **Демо-данные.** В текстах статей были упоминания источников и частных лиц - вычищены. PNG-иконки из генерации
  несли шум и весили 194 КБ - после очистки 17 КБ.

## Тесты

226 тестов: 118 unit, 59 интеграционных на настоящем MySQL и 49 функциональных через приложение целиком
(подробнее - в [architecture.md](architecture.md#тесты)); PHPStan на уровне max без baseline. Новый код приходил
вместе с тестами, ревьюер проверял и их. CI на GitHub Actions гоняет анализ и тесты на PHP 8.1 и 8.5 с MySQL 8.4,
собирает SCSS и образ демо.

## Что решал и проверял я

- Стек и подходы: чистый PHP со своим роутером, Smarty, MySQL 8.4, Docker, SCSS через dart-sass без Node.js,
  PHP 8.5 в окружении при совместимости кода с 8.1.
- Требования к архитектуре: тонкие контроллеры, SQL только в репозиториях, сущности вместо массивов, ленивое
  подключение к базе, без глобального состояния; простота важнее «энтерпрайзности».
- Требования к SEO и скорости: мета-теги и JSON-LD, sitemap, адреса без дублей, кэш статики, лёгкие страницы.
- Широкоформатная вёрстка - моё личное решение: мне так нравится, и я считаю это правильным.
- Две колонки на странице статьи вместо узкой колонки с макета.
- Заглушки для статей без обложки.
- Без поиска: статей мало, а в ТЗ его нет.
- llms.txt и RSS - чтобы блог удобно читали ИИ-агенты и читалки.
- Приёмка каждого этапа: смотрел сайт в браузере на десктопе и телефоне, читал код и замечания ревью, решал,
  что исправлять, и только после этого давал push.
