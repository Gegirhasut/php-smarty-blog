# База данных

MySQL 8.4, InnoDB, `utf8mb4`. Схема - `database/schema.sql`, её целиком применяет `bin/seed.php`; изменения - через
`--fresh`, данные учебные, миграций нет. Время в базе - UTC.

## Схема

- `categories` - `id`, `name`, `slug`, `description`. UNIQUE `slug`.
- `posts` - `id`, `title`, `slug`, `image` (NULL - без обложки), `description`, `content` (MEDIUMTEXT), `views`,
  `published_at` (DATETIME, UTC). UNIQUE `slug`, индексы `published_at` и `views`.
- `category_post` - связь многие-ко-многим: `category_id`, `post_id`, `position`. PK `(category_id, post_id)`,
  UNIQUE `(post_id, position)`, внешние ключи на обе таблицы с каскадным удалением.

Решения:

- **slug в `ascii` с `ascii_bin`** - точное сравнение (`/category/News` не откроет `news`) и компактный индекс.
  Формат проверяет `Slug` до запроса: сравнить такую колонку со строкой с кириллицей MySQL не может (ошибка 3988),
  поэтому чужой адрес отсекается 404 заранее, а сидер такие slug не пускает.
- **`position`** - порядок категорий статьи из её файла сидера, наименьшая позиция - основная категория: она в хлебных
  крошках, первой среди меток, в llms.txt и выбирает заглушку для статьи без обложки. UNIQUE `(post_id, position)`
  не даёт статье двух основных категорий и заодно служит индексом «категории статьи по порядку».
- **`image` может быть NULL** - в ТЗ поле есть, но обязательным не названо.
- **`views` в самой строке статьи.** Просмотр - `UPDATE posts SET views = views + 1`: счётчик увеличивает база,
  одновременные просмотры не теряются. Считается только GET, HEAD шлют боты и проверки ссылок.

## Запросы и индексы

- **Главная** - одним запросом по три свежие статьи каждой категории: `categories JOIN LATERAL (...) ON TRUE`,
  внутри - id статей категории `ORDER BY published_at DESC, id DESC LIMIT 3`. Пустые категории отсекает JOIN,
  колонки карточки и подзапрос основной категории - снаружи, только для выбранных статей. Внутри `posts STRAIGHT_JOIN
  category_post`: статьи идут по индексу даты, связь проверяется по PK, и `LIMIT` обрывает проход. Без подсказки
  MySQL начинает со всех связей категории и сортирует их.
- **Категория** - `COUNT(*)` по PK связки, затем страница: `ORDER BY p.published_at DESC, p.id DESC` (или `p.views`)
  `LIMIT 9 OFFSET n`. `id` в конце сортировки делает порядок стабильным при равных датах и просмотрах, а сама сортировка
  берётся из белого списка: `ORDER BY` не принимает параметры.
- **Похожие статьи** - для каждой категории статьи `LATERAL` берёт 50 последних статей этой категории (без самой
  статьи, тем же проходом по индексу даты), только они группируются: `GROUP BY p.id`, сначала больше общих категорий (`COUNT(*)`), среди равных - новые,
  три штуки. Старая статья с двумя общими категориями, но не из последних 50, может уступить новой с одной. Если таких меньше
  трёх, второй запрос добирает самые свежие из остальных: `WHERE p.id NOT IN (...)` по индексу даты с `LIMIT`.
  Он выполняется только при нехватке, а свежие, в отличие от случайных, дают стабильную страницу.
- **Статья, меню, sitemap, RSS, llms.txt** - поиск по UNIQUE `slug`, `EXISTS` по связке, `MAX(published_at)`
  по категориям, последние 20 статей.

Колонки карточки (`PostCard`) не включают текст статьи, а slug основной категории для заглушки берёт подзапрос
по UNIQUE `(post_id, position)`.

## Что показал EXPLAIN

- **Категория:** `Backward index scan; Using index` по `posts_published_at_index` (или `posts_views_index`) и `eq_ref`
  по PK связки - без filesort и без временной таблицы. Составной индекс `(published_at, id)` не нужен: InnoDB сам
  дописывает первичный ключ в конец вторичного индекса.
- **Главная:** на каждую категорию - `Covering index scan ... posts_published_at_index (reverse)` и
  `Single-row covering index lookup` по PK связки до третьего совпадения; карточки и подзапрос основной категории -
  только для 18 отобранных строк. Без filesort внутри `LATERAL`.
- **Похожие:** своя статья - по UNIQUE `(post_id, position)`, на каждую её категорию - тот же обратный проход
  по индексу даты до 50 кандидатов; временная таблица и сортировка только для них (до 150 строк).
- **Счётчик категории:** только индекс PK связки.

## На больших объёмах: замеры на 100 000 статей

`seed.php --fresh --posts=100000`: 100 049 статей, 199 632 связи, `posts` - 257 МБ при буферном пуле MySQL
по умолчанию 128 МБ. Для маленькой категории добавлена категория на 100 статей (0,1%). Время - медиана пяти
вызовов метода репозитория, план - `EXPLAIN ANALYZE`. «Было» - запросы до `LATERAL` (`ROW_NUMBER()` на главной,
группировка всех соседей в похожих), «стало» - текущие.

| Запрос | Было | Стало | Что в плане сейчас |
|---|---|---|---|
| Главная | 8,8 с | **2,6 мс** | по 3 статьи на категорию обратным проходом по индексу даты, ~18 записей индекса на категорию |
| Похожие для статьи из 3 категорий | 11,8 с | **7,7 мс** | 150 кандидатов, временная таблица на 111 групп |
| Похожие для статьи из 1 категории | 2,9 с | **3,5 мс** | 50 кандидатов |
| Главная с маленькой категорией (100 статей) | - | 9 мс | для неё проход по индексу даты - ~3000 записей ради трёх |
| Похожие для статьи из маленькой категории | - | 150 мс | ~50 000 записей индекса даты ради 50 кандидатов |
| Категория (33 000 статей), страница 1, дата или просмотры | 1 мс | 1 мс | обратный проход по индексу даты (просмотров), `eq_ref` по PK связки |
| Та же категория, `OFFSET 30000` | 1,7 с | 1,7 с | 91 337 записей индекса и 30 009 строк статей ради 9 |
| Маленькая категория (100 статей), страница 1 | 3 мс | 3 мс | MySQL сам выбрал PK связки и filesort 100 строк |
| Счётчик категории | 7 мс | 7 мс | PK связки |

Страница целиком (`curl`, медиана): главная и статьи были 11,5 с и 10,2 с, стали 0,4-0,6 с - столько же, сколько
страница категории с запросом в 1 мс. Остальное - PHP на томе Docker под Windows: `robots.txt` без базы отвечает
за 0,13 с.

Выводы:

- **Главная** больше не перебирает все связи: `LATERAL` с `LIMIT 3` по индексу даты, на объём почти не влияет.
- **Категория:** первые страницы быстрые. Худший случай для обратного прохода по индексу дат - категория в единицы
  процентов: MySQL ещё выбирает индекс, но проходит много чужих статей (отдельно не замерялось).
  Лечится денормализацией `published_at` и `views` в `category_post` с индексами `(category_id, published_at, post_id)`
  и `(category_id, views, post_id)`; цена - просмотры обновлять в двух местах. Глубокий `OFFSET` всё равно проходит
  все пропущенные строки - нужна keyset-пагинация («после такой-то даты и id»).
- **Похожие** группируют не всех соседей, а 50 последних статей каждой категории статьи. Цена - старая статья
  с двумя общими категориями уступает свежей с одной. Добор свежими идёт по индексу даты с `LIMIT` и на объём
  не влияет. Дальше - предрасчёт таблицы `post_similar` по крону или кэш блока.
- **Просмотры:** при большой нагрузке одна популярная строка становится горячей - тогда копить просмотры отдельно
  и записывать пачками.

Что осталось на объёме, честно:

- **Глубокий `OFFSET`** (1,7 с на странице 3334) - нужна keyset-пагинация.
- **Маленькая категория** - проход по общему индексу дат проходит чужие статьи: главная 9 мс, похожие 150 мс.
  Лечится денормализацией `published_at` и `views` в `category_post` (см. выше); не делалась, пока категории
  крупные.

## Сидер

`php bin/seed.php [--fresh] [--posts=N]`. Без `--fresh` создаёт недостающие таблицы и отказывается работать, если данные уже есть;
с `--fresh` удаляет таблицы и применяет схему заново.

Данные - PHP-файлы в `database/seeds`:

- `categories.php` - список категорий (`slug`, `name`, `description`); порядок в файле - порядок в меню и на главной.
- `posts/<slug>.php` - одна статья, имя файла - её slug: `title`, `description`, `image` (необязательно, файл
  из `images/`), `categories` (первая - основная), `published_at` (UTC), `views`, `content`.
- `images/` - обложки; сидер копирует в `public/uploads` только используемые.

Сидер сначала читает и проверяет все файлы (обязательные поля, формат slug, непустой список категорий) и копирует
обложки - если чего-то не хватает, база остаётся пустой. Потом вставляет категории, статьи и связи многострочными
INSERT в одной транзакции: любая ошибка, например неизвестная категория у статьи, откатывает всё. Статьи вставляются
по дате публикации, поэтому старые получают меньшие id.

`--posts=N` добавляет к демо-данным N статей для проверки на объёме (`PostGenerator`, без внешних библиотек): архив
за два года до самой старой демо-статьи, даты растут с номером. Каждая повторяет случайную демо-статью - заголовок
с номером («... (архив №123)»), описание, обложку и основную категорию, - получает ещё до двух категорий и просмотры
до 20 000, текст склеен из вступления образца и двух абзацев других статей; slug - slug образца и номер.
«Случайность» - `mt_rand()` с постоянным seed, поэтому результат всегда один и тот же; статьи выдаются по порядку.
Архив вставляется в той же транзакции до демо-статей пачками по 1000 (id растут вместе с датой); 100 000 статей
локально заливаются за ~40 секунд.
