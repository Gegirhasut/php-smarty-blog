# База данных

MySQL 8.4, InnoDB, `utf8mb4`. Схема - `database/schema.sql`, её целиком применяет `bin/seed.php`; изменения - через
`--fresh`, данные учебные, миграций нет. Время в базе - UTC.

## Схема

- `categories` - `id`, `name`, `slug`, `description`. UNIQUE `slug`.
- `posts` - `id`, `title`, `slug`, `image` (NULL - без обложки), `description`, `content` (MEDIUMTEXT), `views`,
  `published_at` (DATETIME, UTC). UNIQUE `slug`, индексы `published_at` и `views`.
- `category_post` - связь многие-ко-многим: `category_id`, `post_id`, `position`. PK `(category_id, post_id)`,
  UNIQUE `(post_id, position)`, внешние ключи на обе таблицы с каскадным удалением.

Решения:

- **slug в `ascii` с `ascii_bin`** - точное сравнение (`/category/News` не откроет `news`) и компактный индекс.
  Формат проверяет `Slug` до запроса: сравнить такую колонку со строкой с кириллицей MySQL не может (ошибка 3988),
  поэтому чужой адрес отсекается 404 заранее, а сидер такие slug не пускает.
- **`position`** - порядок категорий статьи из её файла сидера, наименьшая позиция - основная категория: она в хлебных
  крошках, первой среди меток, в llms.txt и выбирает заглушку для статьи без обложки. UNIQUE `(post_id, position)`
  не даёт статье двух основных категорий и заодно служит индексом «категории статьи по порядку».
- **`image` может быть NULL** - в ТЗ поле есть, но обязательным не названо.
- **`views` в самой строке статьи.** Просмотр - `UPDATE posts SET views = views + 1`: счётчик увеличивает база,
  одновременные просмотры не теряются. Считается только GET, HEAD шлют боты и проверки ссылок.

## Запросы и индексы

- **Главная** - одним запросом по три свежие статьи каждой категории:
  `ROW_NUMBER() OVER (PARTITION BY c.id ORDER BY p.published_at DESC, p.id DESC)` во вложенном запросе
  и `WHERE place <= 3` снаружи. Пустые категории отсекает JOIN.
- **Категория** - `COUNT(*)` по PK связки, затем страница: `ORDER BY p.published_at DESC, p.id DESC` (или `p.views`)
  `LIMIT 9 OFFSET n`. `id` в конце сортировки делает порядок стабильным при равных датах и просмотрах, а сама сортировка
  берётся из белого списка: `ORDER BY` не принимает параметры.
- **Похожие статьи** - связка соединяется сама с собой: другие статьи тех же категорий, `GROUP BY p.id`,
  сначала больше общих категорий (`COUNT(*)`), среди равных - новые, без самой статьи, три штуки.
- **Статья, меню, sitemap, RSS, llms.txt** - поиск по UNIQUE `slug`, `EXISTS` по связке, `MAX(published_at)`
  по категориям, последние 20 статей.

Колонки карточки (`PostCard`) не включают текст статьи, а slug основной категории для заглушки берёт подзапрос
по UNIQUE `(post_id, position)`.

## Что показал EXPLAIN

- **Категория:** `Backward index scan; Using index` по `posts_published_at_index` (или `posts_views_index`) и `eq_ref`
  по PK связки - без filesort и без временной таблицы. Составной индекс `(published_at, id)` не нужен: InnoDB сам
  дописывает первичный ключ в конец вторичного индекса.
- **Главная:** проход по индексу связки (covering) и сортировка для оконной функции по всем связям - сейчас это
  около 80 строк и доли миллисекунды.
- **Похожие:** своя статья - по UNIQUE `(post_id, position)`, соседи - по PK `(category_id, post_id)`; временная таблица
  и сортировка только для статей тех же категорий.
- **Счётчик категории:** только индекс PK связки.

## На больших объёмах

- **Главная:** вместо нумерации всех связей - `LATERAL` с `LIMIT 3` на каждую категорию по индексу.
- **Категория:** обратный проход по индексу дат проверяет каждую статью на принадлежность категории. Это быстро,
  пока статьи категории - заметная доля всех. Для маленькой категории в большой базе нужен составной индекс по категории
  и дате: перенести `published_at` и `views` в связку (денормализация) и индексы `(category_id, published_at, post_id)`
  и `(category_id, views, post_id)`. Для далёких страниц - keyset-пагинация («после такой-то даты и id») вместо OFFSET.
- **Просмотры:** при большой нагрузке одна популярная строка становится горячей - тогда копить просмотры отдельно
  и записывать пачками.

## Сидер

`php bin/seed.php [--fresh]`. Без `--fresh` создаёт недостающие таблицы и отказывается работать, если данные уже есть;
с `--fresh` удаляет таблицы и применяет схему заново.

Данные - PHP-файлы в `database/seeds`:

- `categories.php` - список категорий (`slug`, `name`, `description`); порядок в файле - порядок в меню и на главной.
- `posts/<slug>.php` - одна статья, имя файла - её slug: `title`, `description`, `image` (необязательно, файл
  из `images/`), `categories` (первая - основная), `published_at` (UTC), `views`, `content`.
- `images/` - обложки; сидер копирует в `public/uploads` только используемые.

Сидер сначала читает и проверяет все файлы (обязательные поля, формат slug, непустой список категорий) и копирует
обложки - если чего-то не хватает, база остаётся пустой. Потом вставляет категории, статьи и связи многострочными
INSERT в одной транзакции: любая ошибка, например неизвестная категория у статьи, откатывает всё. Статьи вставляются
по дате публикации, поэтому старые получают меньшие id.
