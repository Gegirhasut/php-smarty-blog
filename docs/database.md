# База данных

MySQL 8.4, InnoDB, `utf8mb4`. Схема - `database/schema.sql`, её целиком применяет `bin/seed.php`; изменения - через
`--fresh`, данные учебные, миграций нет. Время в базе - UTC.

## Схема

- `categories` - `id`, `name`, `slug`, `description`. UNIQUE `slug`.
- `posts` - `id`, `title`, `slug`, `image` (NULL - без обложки), `description`, `content` (MEDIUMTEXT), `views`,
  `published_at` (DATETIME, UTC). UNIQUE `slug`, индексы `(published_at)` и `(id, published_at, slug)`.
- `category_post` - связь многие-ко-многим: `category_id`, `post_id`, `position` и копии `published_at` и `views`
  статьи. PK `(category_id, post_id)`, UNIQUE `(post_id, position)`, индексы `(category_id, published_at, post_id)`
  и `(category_id, views, post_id)`, внешние ключи на обе таблицы с каскадным удалением.

Решения:

- **slug в `ascii` с `ascii_bin`** - точное сравнение (`/category/News` не откроет `news`) и компактный индекс.
  Формат проверяет `Slug` до запроса: сравнить такую колонку со строкой с кириллицей MySQL не может (ошибка 3988),
  поэтому чужой адрес отсекается 404 заранее, а сидер такие slug не пускает.
- **`position`** - порядок категорий статьи из её файла сидера, наименьшая позиция - основная категория: она в хлебных
  крошках, первой среди меток и выбирает заглушку для статьи без обложки. UNIQUE `(post_id, position)`
  не даёт статье двух основных категорий и заодно служит индексом «категории статьи по порядку».
- **`image` может быть NULL** - в ТЗ поле есть, но обязательным не названо.
- **Дата и просмотры статьи продублированы в связке.** Лента категории сортируется по дате или просмотрам статьи,
  а фильтруется по связке: с индексом только на `posts` MySQL проходит статьи всех категорий подряд, и маленькой
  категории или дальней странице это стоит секунды. Копии в `category_post` дают индекс «категория, дата, id» -
  ровно те записи, что нужны. Цена - копии надо держать равными: связи пишет сидер вместе со статьёй, а просмотр
  увеличивает одним запросом и статью, и её связи. Редактора статей нет; появится - он меняет дату в обоих местах.
- **Просмотр - один `UPDATE` по двум таблицам:** `UPDATE posts p LEFT JOIN category_post cp ON cp.post_id = p.id
  SET p.views = p.views + 1, cp.views = cp.views + 1 WHERE p.id = ?`. Счётчик увеличивает база, одновременные просмотры
  не теряются; один запрос атомарен и не требует транзакции, которая к тому же не открылась бы внутри уже начатой.
  MySQL меняет каждую строку один раз, сколько бы раз она ни встретилась в JOIN: статья из трёх категорий получает +1,
  а не +3 (это проверяет тест), `LEFT JOIN` засчитывает просмотр и статье без категорий. Считается только GET,
  HEAD шлют боты и проверки ссылок.

## Запросы и индексы

- **Главная** - одним запросом по три свежие статьи каждой категории: `categories JOIN LATERAL (...) ON TRUE`,
  внутри - `post_id` из связки `WHERE category_id = c.id ORDER BY category_id DESC, published_at DESC, post_id DESC
  LIMIT 3`. Пустые категории отсекает JOIN, колонки карточки и подзапрос основной категории - снаружи, только для
  выбранных статей. `category_id` в `ORDER BY` внутри одной категории ничего не меняет, но без него MySQL не считает
  категорию из внешней таблицы постоянной, не видит, что индекс уже упорядочен, и сортирует все связи категории.
- **Категория** - `COUNT(*)` по связке, затем отложенное соединение: в подзапросе `post_id` страницы из индекса связки
  `ORDER BY published_at DESC, post_id DESC` (или `views`) `LIMIT 9 OFFSET n`, снаружи - строки этих девяти статей
  по первичному ключу. `OFFSET` пропускает только узкие записи индекса, а не строки статей. id в конце сортировки
  делает порядок стабильным при равных датах и просмотрах, колонка сортировки - из белого списка: `ORDER BY`
  не принимает параметры.
- **Похожие статьи** - кандидаты - соседи статьи по дате в каждой её категории: по 25 записей индекса связки до и после
  её даты (при равной дате - по `post_id`), поэтому у статей одной категории блоки разные. Сначала больше общих категорий,
  затем ближе по дате, затем новее; строки статей - только для трёх выбранных. Запрос на категорию и сторону с `FORCE INDEX`:
  в `LATERAL` MySQL фильтрует категорию целиком, в `UNION` оценивает каждый диапазон спусками по индексу (~1 мс на ветку),
  а без подсказки с параметрами идёт от начала категории. Кандидатов меньше трёх - `WHERE p.id NOT IN (...)` по индексу
  `posts(published_at)` с `LIMIT` добирает самые свежие: в отличие от случайных, они дают стабильную страницу.
- **Sitemap** - `/sitemap.xml` - индекс: файл главной и категорий и файлы статей по 1000, файл N - статьи с id
  от 1000·(N-1)+1 до 1000·N. Число файлов - по наибольшему id, файл - диапазон по узкому покрывающему индексу
  `posts(id, published_at, slug)`, без строк статей с текстом. Дата категории - `MAX(published_at)` по связке
  (по записи индекса на категорию), главной - самая свежая статья. У файлов статей в индексе нет `lastmod`
  (по протоколу необязателен): точная дата файла - `MAX` по его диапазону, то есть проход по всем статьям на каждый
  запрос индекса; даты самих статей - в файлах.
- **llms.txt** - запрос главной с `LIMIT 20`: по 20 свежих статей каждой категории, остальное - по ссылкам
  на категории и sitemap. Статья из нескольких категорий - в разделе каждой, как на главной.
- **Статья, меню, RSS** - поиск по UNIQUE `slug`, `EXISTS` по связке, 20 последних статей по `posts(published_at)`.

Колонки карточки (`PostCard`) не включают текст статьи, а slug основной категории для заглушки берёт подзапрос
по UNIQUE `(post_id, position)`.

## На больших объёмах: 100 000 статей

по умолчанию 128 МБ. Шесть категорий по 31-36 тысяч статей, для проверки добавлены маленькая (каждая тысячная
статья, 100 штук за все два года), крошечная (две самые старые статьи) и пустая. «Было» - код до этих правок, «стало» -
текущий, на тех же данных (генератор детерминирован). Время - медиана пяти вызовов в процессе PHP после прогрева,

Те же страницы через `curl` на `localhost:8080` - 0,3-0,36 с для HTML и 0,15-0,18 с для sitemap и llms.txt:
`robots.txt`, которому база не нужна, отвечает за 0,13 с. Эти 0,15-0,3 с добавляет окружение - PHP и шаблоны на томе
Docker под Windows, - а не запросы.

Что осталось и почему:

- **Глубокий `OFFSET`** проходит все пропущенные записи индекса связки: последняя страница категории на 36 000 статей -
  14 мс, на миллион статей в категории было бы ~0,4 с. Следующий шаг - keyset-пагинация («после такой-то даты и id»)
  для соседних страниц и проход с конца для дальней половины номеров; пока ссылки на последнюю страницу укладываются
  в десятки миллисекунд, номера страниц остаются обычными.
- **Число статей категории** - `COUNT(*)` по её связям, растёт с размером категории (8 мс на 36 000). Дальше - счётчик
  в `categories`, который меняется вместе со связями.
- **Похожие** выбираются среди 25 соседей по дате с каждой стороны в каждой категории статьи: статья с двумя общими
  категориями, но дальше по дате, уступает ближней с одной. Дальше - предрасчёт таблицы `post_similar` по крону или кэш блока.
- **Просмотры:** при большой нагрузке строка популярной статьи и её связи становятся горячими - тогда копить
  просмотры отдельно и записывать пачками.
- **Первая страница большой категории** - 3 мс вместо 1,4: отложенное соединение делает два шага вместо одного.
  Это те же единицы миллисекунд, а последняя страница стала быстрее в сто раз.

## Сидер

`php bin/seed.php [--fresh] [--posts=N]`. Без `--fresh` создаёт недостающие таблицы и отказывается работать, если данные уже есть;
с `--fresh` удаляет таблицы и применяет схему заново.

Данные - PHP-файлы в `database/seeds`:

- `categories.php` - список категорий (`slug`, `name`, `description`); порядок в файле - порядок в меню и на главной.
- `posts/<slug>.php` - одна статья, имя файла - её slug: `title`, `description`, `image` (необязательно, файл
  из `images/`), `categories` (первая - основная), `published_at` (UTC), `views`, `content`.
- `images/` - обложки; сидер копирует в `public/uploads` только используемые.

Сидер сначала читает и проверяет все файлы (обязательные поля, формат slug, непустой список категорий) и копирует
обложки - если чего-то не хватает, база остаётся пустой. Потом вставляет категории, статьи и связи многострочными
INSERT в одной транзакции: любая ошибка, например неизвестная категория у статьи, откатывает всё. Связи получают
дату и просмотры своей статьи. Статьи вставляются по дате публикации, поэтому старые получают меньшие id.

`--posts=N` добавляет к демо-данным N статей для проверки на объёме (`PostGenerator`, без внешних библиотек): архив
за два года до самой старой демо-статьи, даты растут с номером. Каждая повторяет случайную демо-статью - заголовок
с номером («... (архив №123)»), описание, обложку и основную категорию, - получает ещё до двух категорий и просмотры
до 20 000, текст склеен из вступления образца и двух абзацев других статей; slug - slug образца и номер.
«Случайность» - `mt_rand()` с постоянным seed, поэтому результат всегда один и тот же; статьи выдаются по порядку.
Архив вставляется в той же транзакции до демо-статей пачками по 1000 (id растут вместе с датой); 100 000 статей
локально заливаются за ~30 секунд.
